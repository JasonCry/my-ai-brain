# 自动化工程标准作业程序 (Automated Engineering SOPs)

本规范为日常开发中常见场景的标准化作业程序（SOP）。当在对话中感知到用户意图时，Agent **必须自动启动对应 SOP**，并主动输出**「紧凑阶段进度卡片」**，引导用户推进，无需用户手动记忆技能名称或工作流。

---

## 统一交互规范：紧凑阶段进度卡片 (Phase Card)

在进入任何 SOP 时，Agent 每次输出必须以如下统一格式的阶段卡片作为头部引导：

```markdown
> 📌 **[SOP 名称]** `[■■□□□] 阶段 X/Y: 阶段名称` | **关联工单**: `#ID` (若有)  
> **当前目标**: [一句话描述当前步的核心目标]  
> **下一步驱动**: [告知用户接下来需要确认的内容，或直接驱动下一步执行]
```

> **用户跳过与接管机制**：若用户显式说明“跳过”、“直接改”、“紧急修复”，Agent 记录风险后自动降级为 Lite Mode 或直接跳转到用户指定的阶段。

## SOP-1: Bug 缺陷攻坚流 (Bug Triage & Fix SOP)

**触发词**：发现 Bug、出错了、报错、异常、崩溃、不响应、有问题、逻辑不一致等。

### 阶段 1/5: 捕获与建单 (Capture & Issue)
* **卡片标识**：`[■□□□□] 阶段 1/5: 捕获与工单建立`
* **执行动作**：
  1. 梳理用户描述的症状、发生环境（Safari、Chrome、iOS 等）、复现概率。
  2. 执行 `gh issue create --title "..." --body "..."`（若仓库已配置分诊标签则附带 `--label "needs-triage"`）。
  3. 在 `changelog.md` 中对应版本下登记工单。
* **驱动下一步**：向用户汇报生成的 Issue ID，并自动进入阶段 2。

### 阶段 2/5: 建立最小复现闭环 (Feedback Loop)
* **卡片标识**：`[■■□□□] 阶段 2/5: 建立最小复现闭环`
* **执行动作**（参考 `/diagnosing-bugs`）：
  1. **严禁在没有可复现的验证环之前盲目修改业务代码**。
  2. 优先构建可单步执行且必定变红（Fail）的紧致闭环：
     - 优先选：单元测试 / 集成测试（Rust/Flutter）
     - 次优选：curl 脚本、headless 浏览器检查、CLI 探针
  3. 运行并确认该验证环能精确捕获用户描述的症状。
* **驱动下一步**：向用户展示复现命令及红灯输出，推进进入假设阶段。

### 阶段 3/5: 根因假设与探针验证 (Hypotheses & Probes)
* **卡片标识**：`[■■■□□] 阶段 3/5: 根因假设与探针验证`
* **执行动作**：
  1. 提出 3~5 个可证伪的假设（Format: *如果 X 是原因，则改变 Y 会使 Bug 消失*）。
  2. 向用户呈现排序后的假设，并使用带标签的临时日志（如 `[DEBUG-xxxx]`）或断点针对性排查。
* **驱动下一步**：与用户对齐最可能的根因，确认后进入修复阶段。

### 阶段 4/5: TDD 极简修复 (TDD & Minimal Fix)
* **卡片标识**：`[■■■■□] 阶段 4/5: TDD 极简修复`
* **执行动作**（参考 `/tdd` 与 `/ponytail`）：
  1. **Red**：将复现脚本沉淀为正式回归测试用例。
  2. **Green**：编写最少、最直接的修复代码（杜绝过度设计）。
  3. **Refactor**：全量清理 `[DEBUG-xxxx]` 探针代码，确保测试全绿。
* **驱动下一步**：汇报修复改动，准备进行预发验证流水线。

### 阶段 5/5: 预发验证与工单闭环 (Staging Verify & Close)
* **卡片标识**：`[■■■■■] 阶段 5/5: 预发验证与工单闭环`
* **执行动作**：
  1. **Staging First 预发验证**：默认执行 `./scripts/deploy_staging.sh`（部署至 `localhost:3020/3021`），**未经用户明确指令严禁运行 `./scripts/deploy.sh` 触碰生产环境（3000/3001）**。
  2. **研发与发版彻底解耦（铁律）**：日常提交仅做带 `#<Issue_ID>` 的普通 Commit，**严禁修改 `pubspec.yaml` / `Cargo.toml` 版本号，严禁打/推 Git Tag**（仅当用户明确要求正式发版时才调用 `./scripts/publish_release.sh`）。
  3. **反伪闭环四维证据回执**：针对真实 HTTP/MCP 接口与 Safari/Web 控制台完成实测（0 运行时报错），并在结案回复中显式列出四态：`[代码已改] -> [单测已过] -> [真实接口/Staging 3020已测] -> [生产待授权]`，严禁将“单测通过”冒充为“端到端验收完成”。
  4. Git Commit 附带 `#<Issue_ID>`，验证通过后执行 `gh issue close <ID>` 关闭工单。

## ⚡ 轻量通道 (Lite Mode: 2-Step Fast Track)

**判定标准**：纯文案勘误、单个样式微调、静态配置修正，或**单文件内明确的局部逻辑修复（不涉及跨前后端接缝 `UI -> Route -> Storage -> Table` 契约修改、不涉及数据库 Schema 迁移）**。

* **阶段 1/2 [■□]**：登记工单并确认改动点（利用 L0~L2 切片定位，免除多轮 `SKILL.md` 读取开销）。
* **阶段 2/2 [■■]**：遵循 L1 `ponytail` 纪律执行最小修改，先运行 `./scripts/verify_fast.sh` 秒级校验，再运行 `./scripts/deploy_staging.sh`（Staging 3020 快速内循环验证，不改版本号、不触碰生产），提交 `#<Issue_ID>` 并关闭工单。

## SOP-2: 新功能与特性演进流 (Feature Evolution SOP)

**触发词**：新需求、新功能、增加功能、想做一个、支持一下、优化交互等。

### 阶段 1/5: 需求倾听与边界盘问 (Listen & Grilling)
* **卡片标识**：`[■□□□□] 阶段 1/5: 需求倾听与边界盘问`
* **执行动作**（参考 `/grill-me`）：
  - 提取用户的生肉需求，对模糊边界、异常断网、状态并发、多端兼容性进行主动盘问。
  - 明确“做什么”与“明确不做什么（Non-goals）”。

### 阶段 2/5: 领域建模与 ADR 决策 (Domain Modeling & ADR)
* **卡片标识**：`[■■□□□] 阶段 2/5: 领域建模与架构决策`
* **执行动作**（参考 `/domain-modeling`）：
  - 检查是否引入了新概念：更新根目录 `CONTEXT.md`，防止术语混淆。
  - 若涉及系统级重大设计选择，在 `docs/adr/` 下生成一条 ADR 记录。

### 阶段 3/5: 方案设计与任务拆解 (Spec & Tickets)
* **卡片标识**：`[■■■□□] 阶段 3/5: 方案设计与任务拆解`
* **执行动作**（参考 `/to-spec` 与 `/to-tickets`）：
  - 基于 `docs/agents/SPEC.template.md`（含 YAML Frontmatter：`issue_id`、`affected_seams`、`verify_commands`、`acceptance_criteria`），在对应分类子目录 `docs/<category>/<feature_name>_solution.md`（如 `docs/architecture/`、`docs/frontend/` 等，**严禁直接堆放在 `docs/` 根目录**）编写实施 Spec。
  - 使用 `gh issue create` 将需求拆解为结构化子任务。

### 阶段 4/5: 测试驱动实施 (TDD & Implement)
* **卡片标识**：`[■■■■□] 阶段 4/5: 测试驱动实施`
* **执行动作**（参考 `/implement-spec`）：
  - 按照 Spec 逐步实现前后端逻辑，为核心业务逻辑编写测试，保持高内聚低耦合。

### 阶段 5/5: 预发验证与交付闭环 (Staging Verification & Release)
* **卡片标识**：`[■■■■■] 阶段 5/5: 预发验证与交付闭环`
* **执行动作**：
  - 执行 `/code-review` 双轴（Standards + Spec）自检。
  - 运行 `./scripts/deploy_staging.sh` 在 Staging（3020/3021）完成双端联调与真实接口验证（严禁擅自修改版本号或触碰生产 3000/3001）。
  - 输出 `[代码已改] -> [单测已过] -> [真实接口/Staging 3020已测] -> [生产待授权]` 四维回执，关联 `#<Issue_ID>` 提交并关闭工单。

## SOP-3: 架构审视与代码审查流 (Architecture Audit & Review SOP)

**触发词**：架构审查、架构担忧、重构、code review、走查代码、代码膨胀、优化架构等。

### 阶段 1/4: 明确审计范围与焦点 (Scope Definition)
* **卡片标识**：`[■□□□] 阶段 1/4: 明确审计范围与焦点`
* **执行动作**：
  - 锁定用户担忧的核心（如：数据流是否混乱、模块是否过浅、是否存在过度设计、是否违背 Safari 规范）。

### 阶段 2/4: 架构体检与冗余扫描 (Diagnosis & Audit)
* **卡片标识**：`[■■□□] 阶段 2/4: 架构体检与冗余扫描`
* **执行动作**（参考 `/ponytail-audit` 与 `/codebase-design`）：
  - 扫描无用依赖、过度抽象与冗余样板代码（生成减法建议清单）。
  - 评估核心模块接口深度（是否向外暴露了过多内部实现细节）。
  - 对照根目录 `CONTEXT.md` 与 ADR 检查概念一致性。

### 阶段 3/4: 产出重构方案 Spec (Solution Spec)
* **卡片标识**：`[■■■□] 阶段 3/4: 产出重构方案 Spec`
* **执行动作**：
  - 编写 `docs/architecture/<refactor_name>_solution.md`，明确平滑重构路径（分步进行，不破坏现有功能）。

### 阶段 4/4: 双轴 Review 与平滑重构 (Review & Refactor)
* **卡片标识**：`[■■■■] 阶段 4/4: 双轴 Review 与平滑重构`
* **执行动作**（参考 `/code-review`）：
  - 实施重构并进行双轴审查（**Standards 规范轴** + **Spec 功能轴**）。
  - 运行 `./scripts/deploy_staging.sh` 在预发环境确保系统零回归，不擅自触碰生产环境。
